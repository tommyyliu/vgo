vgo-raster-bench -- where rasterization spends its time

  --verify          check the packed writer against the dense one, bit for bit,
                    and exit non-zero on any disagreement. Run this after every
                    change: the raster is a network input, so a difference that
                    looks like rounding is a model that is quietly wrong.

                    It does NOT cover `settled`. Both writers call the same
                    `settled_for_raster`, so a change there passes this gate
                    trivially. What guards settled is
                    `edt::tests::bounded_distance_agrees_with_the_definition`,
                    which pins it against the mathematical definition rather
                    than against the other writer -- run the crate's tests too,
                    not just this.
  --json            machine-readable output, for comparing two builds
  --rounds N        repetitions per measurement, median reported (default 40)
  --size N,...      raster resolution, square (default 256, what runs live)
  --units N,...     board size in stone diameters (default 18,38 -- the two the
                    generator actually plays)
  --stones N,...    stones on the board (default 0,28,60,120,240)

Phases:

  legal      marking which cells a stone could still be played on
  transform  the Euclidean distance transform over that mask
  settled    both, plus the dispatch that chooses between two algorithms
  sweep+out  packed minus settled: nearest/second-nearest stone distances,
             the ridge, and packing the planes

Notes for anyone optimising this:

  Stone count matters more than anything else. Half of generated games are
  38-unit boards running to 312 plies, so the positions that dominate carry
  well over a hundred stones. Measuring at 28 on an 18-unit board understates
  the cost that matters and has already misled several estimates.

  Both writers dispatch on stone count -- `settled` between a contour walk and
  a distance transform, the sweep between a flat scan and a grid search -- so a
  change can improve one side of a threshold and regress the other. Measure
  across the whole --stones range, not one point.

  Run on an idle machine. This measures hundreds of microseconds and anything
  else touching the cache is noise larger than most worthwhile wins.
